# 宇宙之心 v3.0 产品方案：项目驱动的能力包操作系统（审阅版）

> 目标：在 v2.0「商业化学习软件 + 多人协作白板」基础上，进一步升级为 **"项目驱动的能力包操作系统"**。v3.0 不再以"生成知识图谱"为终点，而以"能否把目标拆成可执行项目、把项目拆成能力包、把能力包沉淀为可复用资产"为核心价值。
> 本方案基于 `docs/deep-research-report.md` 中的元学习与项目驱动全周期体系研究，将其转化为可落地的产品架构。

---

## 1. 从 v2.0 到 v3.0 的跃迁

| 维度 | v2.0 | v3.0 |
|---|---|---|
| 核心对象 | 知识图谱、节点、关系 | 项目、能力包、逻辑树、证据链 |
| 学习方式 | AI 辅助理解 + 认知训练 | 项目驱动 + 元学习 + 能力包编排 |
| 协作单位 | 图谱/白板 | 项目工作区 + 阶段门 + 任务流 |
| 评估标准 | 注意力、摘要质量 | 闭环密度、证据完整度、交付物质量 |
| 输出物 | 3D 知识网络 | 逻辑树、任务板、证据库、实验记录、合规报告、复盘模板 |
| 适用框架 | 通用学习 | 商业 / 学术 / 大工程 三种模式 |

**一句话定位**：
> 宇宙之心 v3.0 = 把任意复杂目标转化为可执行项目的 AI 操作系统，帮助个人与团队完成"原理穿透 → 最小实验 → 工程落地 → 运行监控 → 复盘迭代"的全周期闭环。

## 2. 核心概念：能力包与项目全周期

### 2.1 能力包四件套

每个项目目标都可以拆成四个最小充分集合：

| 能力层 | 核心对象 | 典型交付物 | 在软件中的载体 |
|---|---|---|---|
| **知识包** | 原理、概念边界、假设、推导链、失败模式 | 逻辑树、先修图、关键概念闭环卡、FAQ、错误案例库 | 逻辑树工作台 |
| **数据包** | 样本、文献、规范、日志、标注、证据 | 数据卡、证据库、文献矩阵、标签规范、质量报告 | 证据库 |
| **设备包** | 软件环境、实验平台、仿真/硬件、仪器/SOP | 环境清单、部署脚本、校准记录、监控面板 | 实验与原型台 |
| **组织包** | 角色、流程、评审、运营、激励、合规 | WBS、RACI、风险台账、审查门、决策日志 | 项目驾驶舱 + 合规治理台 |

### 2.2 七步项目闭环

v3.0 把学习/执行抽象为一条可无限回溯的七步闭环：

```text
问题定义 → 原理建模 → 最小实验 → 工程实现 → 场景落地 → 运行监控 → 复盘迭代
```

每一步都必须留下**证据、状态、决策记录**。如果某一步未达门槛，系统自动回溯到上游薄弱节点，而不是继续"假装理解"。

### 2.3 三种项目模式

v3.0 在底层支持三种不同的"真相单位"与优化函数：

| 模式 | 真相单位 | 优化目标 | 默认输出物 |
|---|---|---|---|
| **商业框架** | 用户是否愿意持续付费/使用 | 市场验证速度、资源回收、可扩展性 | 问题访谈脚本、MVP 计划、运营指标、商业模式画布 |
| **学术框架** | 结论是否可证伪、可复现、可共享 | 方法严谨性、数据治理、知识贡献 | 预注册方案、方法部分、数据包、复现脚本、论文结构 |
| **大工程框架** | 系统是否在边界条件下安全、可靠、可维护 | 需求一致性、接口控制、验证矩阵、全寿命周期成功率 | 需求追踪矩阵、接口控制文档、验证计划、维护手册 |

用户创建项目时选择一个主模式，系统据此调整默认模板、审查门和输出格式。

## 3. v3.0 六大核心界面模块

### 3.1 项目驾驶舱（Project Cockpit）

- **目的**：看全局目标、阶段、风险、阻塞。
- **关键控件**：
  - 目标卡：一句话项目目标 + 成功判据
  - 阶段门：当前所处七步闭环阶段
  - 里程碑：可交付节点与截止时间
  - 健康状态：知识/数据/设备/组织四包完整度
  - 协作者状态：在线成员、最近编辑、锁定节点
- **自动化动作**：自动汇总任务、证据、风险、下一步建议。

### 3.2 逻辑树工作台（Logic Tree Workbench）

- **目的**：把项目目标展开为无限可嵌套的逻辑树，每个节点绑定证据、任务、风险、交付物。
- **关键控件**：
  - 树形/3D 双视图切换（继承 v2.0 3D 图谱能力）
  - 节点类型：目标、原理、变量、设备、数据、组织、维护、风险、验证、证据
  - 先修依赖：自动识别上游缺失节点
  - 证据强度：每个节点显示证据充分度
  - 反例区：记录与当前节点矛盾的证据
- **自动化动作**：
  - 自动展开节点
  - 识别依赖缺口
  - 当实验失败时自动回溯到上游节点

### 3.3 证据库（Evidence Library）

- **目的**：管理文献、数据、实验、会议纪要，支持"支持 / 反对 / 待验证"三栏分类。
- **关键控件**：
  - 文献卡、数据卡、实验卡、决策卡
  - 版本管理、来源追踪
  - 冲突证据高亮
  - 与逻辑树节点双向绑定
- **自动化动作**：
  - 从 PDF/论文中抽取 claim、方法、指标、合规点
  - 自动识别证据冲突
  - 生成证据矩阵

### 3.4 实验与原型台（Experiment & Prototype Bench）

- **目的**：组织实验、仿真、代码、部署，记录参数、结果、失败类型。
- **关键控件**：
  - 实验模板库
  - 指标面板
  - 代码/脚本版本绑定
  - 环境清单
  - 一键回滚
- **自动化动作**：
  - 自动记录实验参数与结果
  - 失败类型分类
  - 根据结果更新逻辑树状态

### 3.5 合规与治理台（Compliance & Governance Console）

- **目的**：管理受试者、隐私、AI 风险、审批流，把合规从"事后补文档"变成"内置控制点"。
- **关键控件**：
  - 同意记录管理
  - 数据分级与用途标注
  - 审查门（Review Gate）
  - 审计日志
  - 角色权限矩阵
- **自动化动作**：
  - 根据项目类型自动触发合规检查
  - 高风险操作强制人工复核
  - 生成合规报告

### 3.6 复盘与模板库（Retrospective & Template Library）

- **目的**：沉淀失败模式、最佳实践、可复用能力包。
- **关键控件**：
  - 失败模式库
  - 最佳实践库
  - 能力包模板市场
  - 项目复盘报告
- **自动化动作**：
  - 把复盘结果回写到项目模板
  - 推荐相似项目的失败模式与解决方案

## 4. v3.0 数据模型扩展

在 v2.0 的 `Workspace`、`Project`、`GraphNode`、`GraphLink` 基础上，v3.0 引入以下核心实体：

| 实体 | 说明 |
|---|---|
| `CapabilityPackage` | 知识/数据/设备/组织四包，可挂载到项目或节点 |
| `LogicTreeNode` | 逻辑树节点，与 GraphNode 可互转 |
| `Evidence` | 证据条目，支持多模态输入与三栏分类 |
| `Experiment` | 实验记录，含参数、结果、失败类型 |
| `ReviewGate` | 审查门，含通过条件、审批人、审计日志 |
| `DecisionLog` | 决策日志，记录谁在什么时间做了什么决定 |
| `RiskItem` | 风险台账，含等级、应对措施、责任人 |
| `Template` | 可复用模板，含能力包、逻辑树、实验模板 |
| `Retrospective` | 复盘报告，关联到项目与模板 |

## 5. v3.0 关键交互流程

```text
用户输入目标或项目题目
    ↓
任务澄清与边界设定（AI 教练角色）
    ↓
自动生成能力包草案 + 选择项目模式（商业/学术/大工程）
    ↓
构建逻辑树与先修节点图
    ↓
生成学习冲刺与最小实验
    ↓
执行任务与采集证据
    ↓
自动评估：概念掌握 / 结果质量 / 风险状态
    ↓
是否达到门槛？
    ├─ 否 → 回溯薄弱节点 → 重新构建/补洞
    └─ 是 → 形成原型或研究产物
              ↓
    部署 / 投稿 / 评审 / 验收
              ↓
    运行监控与复盘
              ↓
    更新知识图谱、模板与能力包
```

## 7. v3.0 新增算法与 AI 能力

### 7.1 闭环密度评估

衡量单位时间内完成"假设—验证—修正—沉淀"循环的次数：

```text
闭环密度 = (完成的任务数 × 证据完整度 × 验证通过率) / 项目持续时间
```

### 7.2 能力包完整度评分

对知识/数据/设备/组织四包分别打分，低于阈值时触发补洞建议。

### 7.3 逻辑树健康度

- 依赖缺口检测
- 循环依赖检测
- 证据冲突检测
- 关键路径识别

### 7.4 项目模式适配 AI

根据项目模式自动调整：
- 提示词模板
- 默认审查门
- 输出物格式
- 合规检查清单

## 9. 风险与边界

| 风险 | 说明 | 缓解 |
|---|---|---|
| 项目模式法律合规 | 医学/金融/航空等场景有专门法规 | 默认提供通用模板，行业模板需法务审核后上架 |
| 证据链真实性 | 用户可能上传伪造证据 | 保留审计日志，提供可信度徽章，但不替代专业鉴定 |
| 过度结构化 | 可能增加用户认知负担 | 允许从简单模式开始，逐步启用高级功能 |
| 闭环密度游戏化 | 用户可能追求数量而牺牲质量 | 综合质量评分，而非单一指标 |

## 11. 结论

v3.0 不是 v2.0 的简单功能叠加，而是**产品范式的升级**：从"知识管理工具"进化为"项目驱动的能力包操作系统"。它的护城河不在于某个单一功能，而在于能否把"目标—能力包—逻辑树—证据—实验—复盘"这一整套闭环做得足够流畅、可验证、可复用。

建议在 v2.0 商业化验证后，立即启动 v3.0 的能力包数据模型与项目驾驶舱原型开发。
