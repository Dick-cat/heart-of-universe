# 宇宙之心 v3.0 流程设计：项目驱动的能力包操作系统

> 本文档定义 v3.0 的核心用户流程、阶段门、数据流与 AI 协作方式。
> 基于 `docs/v3_0_PROPOSAL.md` 与 `docs/deep-research-report.md` 中的"能力包四件套"与"七步闭环"思想。

---

## 1. 设计目标

v3.0 的流程不是把 v2.0 的"知识图谱编辑"拉长，而是把任何学习目标或项目目标转化为一条**可执行、可验证、可沉淀**的流水线：

- **输入**：一个模糊的目标、一个问题、一篇论文、一个需求。
- **过程**：目标澄清 → 能力包拆分 → 逻辑树构建 → 证据采集 → 最小实验 → 工程实现 → 场景验证 → 运行监控 → 复盘迭代。
- **输出**：可交付的成果 + 可复用的能力包模板 + 更新的个人/团队知识图谱。

---

## 2. 用户入口（Entry Points）

| 入口 | 适用场景 | 初始动作 |
|---|---|---|
| **从零开始** | 用户只有一个想法 | 进入目标澄清对话 |
| **从 v2 图谱升级** | 已有知识网络，想围绕某个节点做项目 | 选中节点 → "以此为中心创建项目" |
| **从模板开始** | 做论文、做产品、做实验 | 选择领域模板 → 填入变量 |
| **从文档/论文导入** | 拿到一篇论文或需求文档 | 上传 PDF → 自动抽取目标与能力包草案 |

## 4. 各阶段详细设计

### Phase 0: 目标澄清与模式选择

**目标**：把模糊想法变成可验证的项目目标。

**流程**：

1. **AI 教练访谈**：通过 3–7 轮对话，询问：
   - 你想解决什么问题？
   - 成功的具体标准是什么？
   - 目标用户/受众是谁？
   - 时间、资源、技能约束？
   - 已知什么？未知什么？
2. **模式选择**：系统推荐项目模式：
   - **商业框架**：优化付费/使用、市场验证速度
   - **学术框架**：优化可证伪、可复现、方法严谨
   - **大工程框架**：优化可靠性、接口控制、验证矩阵
3. **生成项目目标卡**：
   - 一句话目标
   - 3–5 条可量化成功判据
   - 边界与排除项
   - 默认审查门

**输出**：`ProjectGoalCard`

**阶段门（Gate 0）**：
- [ ] 目标足够具体，可拆分为子任务
- [ ] 成功判据可量化或至少可判定
- [ ] 项目模式已确认

---

### Phase 1: 能力包草案生成

**目标**：把目标拆成四包最小充分集合。

**流程**：

1. **AI 生成草案**：根据项目目标与模式，生成：
   - **知识包**：必须掌握的原理、概念、假设、推导链
   - **数据包**：需要的样本、文献、规范、日志、标注
   - **设备包**：软件环境、实验平台、硬件/SOP
   - **组织包**：角色、流程、评审、合规、运营
2. **用户编辑与确认**：拖拽调整、增删、标注优先级。
3. **缺口识别**：标记当前缺失或薄弱的能力包。

**输出**：`CapabilityPackage` × 4

**阶段门（Gate 1）**：
- [ ] 四包覆盖了目标达成所需的最小充分条件
- [ ] 每包至少有一条核心交付物
- [ ] 缺失项已标注并分配获取计划

---

### Phase 2: 逻辑树构建

**目标**：把能力包展开为可执行、可追踪的逻辑树。

**流程**：

1. **自动展开**：以目标为根，递归生成子目标/子假设/子任务。
2. **节点类型标注**：
   - 目标、原理、变量、设备、数据、组织、维护、风险、验证、证据
3. **依赖关系建立**：
   - 先修依赖（prerequisite）
   - 支持关系（supports）
   - 反驳关系（contradicts）
   - 验证关系（validates）
4. **风险与反例节点**：在每个关键节点下自动创建"失败模式"子节点。
5. **关键路径计算**：标出必须优先完成的节点链。

**输出**：`LogicTree`

**阶段门（Gate 2）**：
- [ ] 逻辑树覆盖所有能力包
- [ ] 关键路径上的节点无未解决的先修依赖
- [ ] 每个叶子节点对应可执行任务或证据

---

### Phase 3: 证据采集与审查

**目标**：为逻辑树节点填充可信证据，识别冲突与缺口。

**流程**：

1. **多源搜索**：
   - 学术数据库：OpenAlex、arXiv、PubMed、Semantic Scholar
   - 开放网络：官方文档、权威百科、数据集
   - 本地文档：PDF、笔记、 previously imported papers
2. **证据抽取**：从每篇文献/文档中提取：
   - Claim（论断）
   - Method（方法）
   - Evidence（数据/实验）
   - Scope（适用范围）
   - Limitation（局限）
3. **证据分类**：对每个 evidence 标记：
   - 支持 / 反对 / 待验证 / 无关
4. **冲突检测**：自动找出相互矛盾的证据并高亮。
5. **AI 严格审查**：按 `docs/EVIDENCE_REVIEW_FOUNDATION.md` 五维度输出问题清单。

**输出**：`EvidenceLibrary` + `EvidenceMatrix`

**阶段门（Gate 3）**：
- [ ] 关键节点至少有一条可信证据
- [ ] 冲突证据已标注并计划解决
- [ ] 无 critical 级别未解决的审查问题

---

### Phase 4: 最小实验/原型

**目标**：用最小成本验证关键假设。

**流程**：

1. **实验设计**：为每个高风险/高不确定性节点生成最小实验：
   - 假设
   - 变量与指标
   - 最小样本量
   - 所需环境
   - 成功/失败判据
2. **环境清单**：自动检查并列出所需软件、数据、硬件。
3. **执行记录**：
   - 参数快照
   - 中间结果
   - 失败类型分类
   - 异常与修正
4. **结果回写**：根据实验结果自动更新逻辑树节点状态：
   - 验证通过 / 验证失败 / 需重新设计

**输出**：`ExperimentRecord`

**阶段门（Gate 4）**：
- [ ] 关键假设至少有一个实验验证
- [ ] 实验结果已记录并链接到逻辑树
- [ ] 失败实验已分类并产生下一步动作

---

### Phase 5: 工程实现与整合

**目标**：把验证后的方案转化为可交付物。

**流程**：

1. **任务拆分**：从逻辑树生成 WBS（工作分解结构）。
2. **RACI 分配**（团队模式）：明确负责人、执行人、咨询人、知情人。
3. **进度追踪**：看板视图，关联逻辑树节点。
4. **文档生成**：根据项目模式自动生成：
   - 商业：MVP 计划、运营指标、商业模式画布
   - 学术：方法部分、数据包、复现脚本、论文结构
   - 工程：需求追踪矩阵、接口控制文档、验证计划
5. **关系补全**：把新产生的交付物节点自动链接回逻辑树。

**输出**：`Deliverable` + `TaskBoard`

**阶段门（Gate 5）**：
- [ ] 所有关键路径节点已转化为任务或交付物
- [ ] 交付物与逻辑树节点双向链接
- [ ] 关键文档已生成并通过初审

---

### Phase 6: 场景验证与落地

**目标**：在真实或仿真场景中验证交付物是否满足目标。

**流程**：

1. **验证方案**：根据成功判据设计验证实验或用户测试。
2. **收集反馈**：
   - 商业：用户访谈、A/B 测试、付费意愿
   - 学术：同行预审、复现实验、公开数据集
   - 工程：压力测试、边界测试、验收测试
3. **差距分析**：对照成功判据，标记未达标项。
4. **生成迭代任务**：把差距转化为新的逻辑树节点或实验。

**输出**：`ValidationReport`

**阶段门（Gate 6）**：
- [ ] 至少完成一轮场景验证
- [ ] 验证结果与成功判据对齐
- [ ] 未达标项已转化为可执行任务

---

### Phase 7: 运行监控

**目标**：长期追踪项目成果的表现与健康度。

**流程**：

1. **指标面板**：连接数据源，持续显示关键指标。
2. **告警规则**：定义异常阈值，触发复核任务。
3. **维护日志**：记录更新、修复、退化。
4. **知识回流**：把运行中发现的新问题/新证据回写到逻辑树。

**输出**：`OperationDashboard` + `MaintenanceLog`

**阶段门（Gate 7）**：
- [ ] 关键指标可监控
- [ ] 告警与维护流程已建立

---

### Phase 8: 复盘与模板化

**目标**：把项目经验沉淀为可复用资产。

**流程**：

1. **闭环密度分析**：统计"假设—验证—修正—沉淀"循环次数与质量。
2. **失败模式入库**：把项目中的失败类型、原因、解决方案写入失败模式库。
3. **最佳实践提取**：识别可复用的 SOP、模板、检查清单。
4. **能力包打包**：把四包内容整理成模板，供下次项目直接使用。
5. **发布/分享**：可选择分享到团队模板市场或保持私有。

**输出**：`RetrospectiveReport` + `CapabilityPackageTemplate`

**阶段门（Gate 8）**：
- [ ] 复盘报告已生成
- [ ] 至少一个能力包模板已沉淀
- [ ] 失败模式/最佳实践已入库

## 5. 审查门与回溯机制

每个阶段门都是一个**强制检查点**。未通过时，系统不允许进入下一阶段，而是生成**回溯任务**：

```text
Gate 未通过
    │
    ▼
定位最上游的薄弱节点
    │
    ▼
生成补洞任务（学习、搜索、实验、修正）
    │
    ▼
补洞完成后重新触发 Gate
```

**AI 在 Gate 中的角色**：
- 自动检查清单项
- 高亮未满足条件
- 推荐回溯路径
- 不替用户做最终通过决策

## 6. 三种项目模式的差异

| 维度 | 商业框架 | 学术框架 | 大工程框架 |
|---|---|---|---|
| 默认模板 | 商业模式画布、用户访谈、MVP | 预注册、方法、数据、论文 | 需求矩阵、接口控制、验证计划 |
| Gate 权重 | 市场验证 > 成本 > 速度 | 方法严谨 > 可复现 > 来源 | 安全/可靠 > 接口一致 > 维护 |
| 证据偏好 | 用户行为数据、市场数据 | 同行评审、公开数据、代码 | 测试报告、标准规范、审计日志 |
| 失败处理 | pivot / 调整价值主张 | 修正假设、补实验、重分析 | 回滚、加固、变更控制 |
| 输出物 | 产品、运营指标、商业计划 | 论文、数据集、复现包 | 系统、手册、验证报告 |

## 8. AI 角色设计

v3.0 不是单一 AI，而是多个 AI Agent 协作：

| Agent | 职责 | 出现阶段 |
|---|---|---|
| **项目教练** | 澄清目标、拆解能力包、把控节奏 | 全程 |
| **领域专家** | 生成逻辑树、解释原理、推荐学习路径 | Phase 1–2 |
| **文献研究员** | 搜索、抽取、 summarize、生成证据矩阵 | Phase 3 |
| **实验设计师** | 设计最小实验、推荐工具、分析结果 | Phase 4 |
| **审稿人/红队** | 审查证据、找漏洞、提出反例 | Phase 3, 5, 6 |
| **合规官** | 检查伦理、隐私、安全、方法规范 | Phase 0, 4, 6 |
| **复盘助手** | 提取失败模式、生成模板建议 | Phase 8 |

这些 Agent 在底层都是 LLM 调用，但拥有不同的：
- 系统提示词
- 可用工具（搜索、代码执行、审查清单）
- 输出格式
- 调用时机

## 9. 与 v2.0 的衔接

| v2.0 资产 | v3.0 如何使用 |
|---|---|
| 知识图谱节点 | 作为逻辑树的输入/子树 |
| 关系 | 转化为依赖、支持、反驳关系 |
| 附件 | 进入数据包/证据库 |
| 注意力/视觉监督数据 | 用于评估学习/工作投入质量 |
| 认知训练记录 | 用于评估知识掌握程度 |
| 证据审查结果 | 直接用于 Gate 3 |
| 学术搜索 | 直接用于 Phase 3 |

## 10. MVP 范围建议

v3.0 范围很大，建议按以下顺序验证：

1. **先做 Phase 0–2 + 项目驾驶舱 + 逻辑树工作台**（验证"目标拆成能力包再拆成树"的核心价值）
2. **再做 Phase 3 证据库 + 学术搜索接入**
3. **再做 Phase 4 实验台 + Phase 8 复盘模板库**
4. **最后做 Phase 5–7 的复杂工作流与团队权限**

---

## 11. 需要决策的问题

1. v3.0 是否先只做**单人项目模式**，还是一开始就要支持**团队协作**？
2. 项目模板是官方预设为主，还是优先让用户/社区贡献？
3. 实验台是否需要真正的代码执行环境（如 Jupyter-lite、本地 Python），还是只记录实验参数与结果？
4. 是否需要与 v2.0 共享同一个底层数据存储（GraphNode 扩展），还是独立一套项目数据模型？
5. AI Agent 是单次 LLM 调用模拟多角色，还是每个 Agent 独立调用并可以互相引用上下文？
